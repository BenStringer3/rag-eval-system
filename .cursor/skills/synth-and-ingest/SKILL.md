# Synth-and-ingest skill

## Purpose

Read a user-specified corpus directory, understand its contents deeply, generate high-quality synthetic Q&A evaluation pairs that are **directly and specifically grounded** in the actual documents, write `data/eval_datasets/synthetic.json`, then ingest the corpus into the vector store.

---

## Step 1 — Verify read access and enumerate the corpus

1. Confirm the corpus directory exists and you can read it (use `Glob` with `<dir>/**/*`).
2. If the directory does not exist or is empty, stop and report the issue clearly.
3. List all files. Prefer these types (skip binaries, images, lock files):
   - `*.md`, `*.txt`, `*.rst` — prose and documentation
   - `*.sh`, `*.py`, `*.yaml`, `*.yml`, `*.json`, `*.conf`, `*.toml` — configuration and scripts
   - `*.service`, `*.socket`, `*.timer` — systemd units
   - Any file without extension that looks like a script

---

## Step 2 — Read and internalise every relevant file

**Read every non-binary file** using the `Read` tool. Do not skim. For each file, note:
- What problem it solves or what it configures
- Key facts: user names, file paths, service names, flags, thresholds, commands, sequences, gotchas
- Any warnings or caveats explicitly stated
- How this file relates to others (e.g. install.sh references files in systemd/)

This is the most important step. The quality of every Q&A pair depends entirely on how thoroughly you understand the corpus.

---

## Step 3 — Design the Q&A pairs

**Minimum 10 pairs**, more if the corpus is large or diverse. Aim for **15–20** for a typical project repo.

### Quality criteria for each pair

- **Specific, not vague**: "What systemd unit file starts the Sunshine streaming service, and what user does it run as?" is good. "What does Sunshine do?" is bad.
- **Directly answerable from the corpus**: The expected_answer must be a fact that literally appears in at least one document — a path, a username, a flag, a command, a sentence.
- **Diverse** across:
  - Documents (spread across files, not just the README)
  - Difficulty: easy (single fact), medium (requires combining 2 concepts), hard (requires understanding a workflow or interaction between components)
  - Categories: match the natural topic clusters of the corpus (e.g. "install", "systemd", "networking", "xorg", "streaming", "moonlight", "security")
- **Unambiguous**: the expected_answer should be the one correct answer; avoid questions where multiple different answers would be equally valid
- **No "what is this project about?" generics**: all pairs must be corpus-specific

### ID scheme

Use sequential IDs: `syn001`, `syn002`, … Preserve existing IDs if the file already has entries you want to keep; renumber only if there are conflicts.

### Metadata

- `category`: short snake_case label matching the primary document topic (e.g. `install`, `moonlight`, `systemd`, `xorg`, `networking`, `security`, `moondeck`)
- `difficulty`: `easy` | `medium` | `hard`

---

## Step 4 — Write data/eval_datasets/synthetic.json

Write the complete JSON file. The schema is:

```json
{
  "name": "synthetic",
  "description": "Corpus-grounded eval pairs synthesized from <corpus_dir>. Auto-generated by synth-and-ingest skill.",
  "version": "0.1.0",
  "samples": [
    {
      "id": "syn001",
      "query": "...",
      "expected_answer": "...",
      "expected_context": null,
      "metadata": {"category": "...", "difficulty": "easy|medium|hard"}
    }
  ]
}
```

`expected_context` should remain `null` unless you have a very specific chunk excerpt you want to enforce verbatim retrieval of.

After writing, confirm: every `expected_answer` is grounded in a document you read in Step 2. If any answer is vague or generic, revise it to cite a concrete detail.

---

## Step 5 — Run ingest

```bash
python -m src.rag.ingest --corpus-dir <dir>
```

Run from the repo root (`/home/ben/repos/rag-eval-system`). If you want a clean index, add `--reset`. Report the number of chunks indexed.

---

## Step 6 — Report back

Tell the user:
- How many files you read and from which subdirectories
- How many Q&A pairs were written and a brief breakdown by category and difficulty
- The ingest result (chunk count)
- Any files you skipped and why

## Repo touchpoints

- **Output:** `data/eval_datasets/synthetic.json`
- **Ingest CLI:** `src/rag/ingest.py` (calls `src/rag/pipeline.py` → `pipeline.ingest(corpus_dir)`)
- **Schema:** `src/data/schemas.py` → `EvalSample`, `EvalDataset`
- **Eval config:** `configs/eval.yaml` → `datasets.synthetic` — confirm `enabled: true` so the file is picked up by `scripts/run_eval_report.py`
- **Existing pairs:** `data/eval_datasets/synthetic.json` — read first; preserve any high-quality hand-written pairs unless the user says to replace all

---

## Anti-patterns to avoid

- Do NOT write questions about concepts not present in the corpus (e.g. Kubernetes, AWS, if the corpus has no such content)
- Do NOT write expected_answers that describe what the system "generally" does — cite specifics
- Do NOT write duplicate or near-duplicate questions
- Do NOT skip files because they look like config — config files are often the richest source of ground-truth facts
- Do NOT run `--reset` on the ingest unless the user asks for it; it destroys the existing index
